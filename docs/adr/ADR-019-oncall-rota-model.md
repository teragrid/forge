# ADR-019 — On-call rota model

- **Status:** Proposed
- **Tracker:** ARCH-DEC-19
- **Spec/Arch anchor:** Arch §18.2, OPS-16, Spec §16.5.8 (eligibility ladder)
- **Decision date:** TBD
- **Deciders:** Delivery lead
- **Consulted:** Core engineering, DevSecOps, security WG

## Context

Without a published rota, S0/S1 incidents page no one. Forge's tiered governance (Spec §16.5.8) requires:

- A rota with eligibility constraints (Maintainer-tier or above).
- Predictable schedule for both core engineers and community contributors who opt in.
- Public publication so reporters know who to expect.
- Tooling that survives a single absent on-call (escalation chain).

## Decision

Forge will run a **weekly on-call rotation** with one **Primary** and one **Secondary** per week, scheduled by a script in `scripts/oncall-rotate.{rs,py}`. Eligibility tiers, paging tooling, and publication contract:

### Eligibility

- **Primary:** Maintainer-tier or above (Spec §16.5.8).
- **Secondary:** Reviewer-tier or above; backup for Primary.
- **Security pager** (separate but co-rotating): Security-WG members only, satisfies ADR-018 first-response SLAs.

A volunteer can opt OUT of any week with ≥ 14 days' notice; the script auto-fills.

### Schedule

- Rotation cadence: **weekly**, Monday 09:00 UTC handover.
- Maximum continuous on-call: 2 weeks (forced gap of ≥ 4 weeks after).
- Holidays: respected per declared TZ in `oncall-roster.yml`.

### Escalation chain

1. Page Primary (PagerDuty / Opsgenie / equivalent — see "Tooling" below).
2. After 15 min unack → page Secondary.
3. After 15 min unack → page Delivery lead.
4. After 30 min unack → broadcast in `#forge-incident` channel.

### Tooling

**Primary choice: PagerDuty** (free tier covers ≤ 5 users; sufficient pre-1.0).
**Fallback:** Opsgenie free tier (if PagerDuty pricing changes); or a self-hosted [`PagerCenter`](https://github.com/PagerCenter/) deployment.

Webhook integrations:

- GitHub Issues label `severity:S0` / `S1` → PagerDuty incident.
- Status-page (per ADR-021) outage state-transition → page on-call.
- Failed CI on `main` → notify (not page) in channel.

### Publication contract (`docs/oncall/`)

- `docs/oncall/README.md` — current Primary + Secondary, rotation rules, escalation chain.
- `docs/oncall/roster.yml` — source of truth (machine-readable: members, TZ, opt-out periods).
- `docs/oncall/schedule-YYYY-Q.md` — published quarterly schedule (auto-generated from `roster.yml`).
- Updated within 24 h of any change by the rotation script.

### Burnout guards

- Hard cap: no person on Primary > 6 weeks per quarter.
- Voluntary "shadow week" before first solo Primary shift.
- Quarterly retro on incident count + paging volume → adjust roster.

## Alternatives considered

### Option A — Follow-the-sun multi-region (rejected pre-1.0)

Pros: no overnight pages.
Cons: requires ≥ 6 maintainers in 3 TZs; not realistic until post-1.0.

### Option B — No on-call, best-effort response (rejected)

Pros: zero overhead.
Cons: violates §18.2 reporter-feedback contract; reputation-damaging.

### Option C — Single permanent on-call (rejected)

Pros: clear ownership.
Cons: burnout guaranteed.

## Consequences

### Positive

- Clear, public, predictable response.
- Eligibility ladder integrates with Spec §16.5.8 governance.
- Burnout guards are encoded, not improvised.

### Negative / accepted trade-offs

- PagerDuty free tier is an external dependency; documented exit plan exists (Opsgenie / self-host).
- Pre-1.0, the rotation has only a few people; mitigated by Delivery-lead escalation path.

### Follow-ups created

- DEV-M0-23 — `oncall-rotate` script + `roster.yml` schema.
- OPS-16 — quarterly schedule publication.
- ADR-018 dependency: security pager is a co-rotating but separate roster.

## Compliance hooks

- Test: `oncall-rotate --check` lints `roster.yml` against schema (TEST-29-related).
- Audit: monthly check that an incident's first-response timestamp ≤ SLA per severity.
- Docs: `docs/oncall/README.md` regenerated by the rotation script (drift = CI failure).
