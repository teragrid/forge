# spec.yml Schema Reference

`spec.yml` is the machine-readable counterpart of `spec.md`.  It is written
alongside `spec.md` in `.forge/specs/<slug>/` whenever `forge ship` runs the
**Spec** checkpoint.  Downstream checkpoints (Test, Breakdown, Ship) read
`spec.yml` instead of parsing prose Markdown.

> **Do not edit `spec.yml` by hand.**  Edit `spec.md` and re-run
> `forge ship spec` to regenerate it.

---

## File location

```
.forge/specs/<slug>/spec.yml
```

where `<slug>` is a URL-safe identifier derived from the feature description
(e.g. `auth-email-verification`).

---

## Fields

| Field | Type | Required | Description |
|---|---|---|---|
| `schema_version` | integer | yes | Always `1` for this version. |
| `id` | string | yes | URL-safe slug, matches the directory name. |
| `feature` | string | yes | Original feature description passed to `forge ship`. |
| `status` | string | yes | Lifecycle stage: `draft` \| `active` \| `done`. |
| `created_at` | string | no | RFC-3339 UTC timestamp when the manifest was first written. |
| `acceptance_criteria` | list[string] | no | Structured criteria extracted from `spec.md` (Given/When/Then or free-form). |
| `scan_policy.families` | list[string] | yes | Scanner families to run at the Ship checkpoint. |
| `events_emitted` | list[string] | no | Domain events extracted from `event:` lines in `spec.md`. |
| `authz_model` | string | no | Authorization model note extracted from the first `authz:` line in `spec.md`. |

---

## `scan_policy.families`

The default set includes all eight scanner families:

| Family | What it checks |
|---|---|
| `secrets` | Hardcoded credentials, API keys, tokens |
| `sca` | Open-source dependency vulnerabilities (CVEs) |
| `sast` | Static application security testing |
| `license` | OSS license compliance |
| `iac` | Infrastructure-as-Code misconfigurations |
| `container` | Container image vulnerabilities |
| `api` | REST/gRPC API security issues |
| `supply-chain` | Build pipeline and dependency integrity |

To restrict scanning for a feature, add an `authz:` line to `spec.md` — or
edit `spec.yml` only if you understand that it will be overwritten on the next
`forge ship spec` run.

---

## Example

```yaml
# forge spec manifest — auto-generated by `forge ship spec`
# Edit spec.md instead; this file is regenerated on each `forge ship spec` run.
schema_version: 1
id: auth-email-verification
feature: auth email verification
status: draft
created_at: "2024-11-01T12:00:00Z"
acceptance_criteria:
  - "Given a new user, when they register, then a verification email is sent"
  - "Given an unverified user, when they click the link, then their account is activated"
scan_policy:
  families:
    - secrets
    - sca
    - sast
    - license
    - iac
    - container
    - api
    - supply-chain
events_emitted:
  - UserRegistered
  - EmailVerified
authz_model: "RBAC with role=unauthenticated allowed"
```

---

## Extraction rules

`forge ship spec` extracts structured data from `spec.md` using these rules:

- **Acceptance criteria** — lines starting with `- [ ]` or `- [x]`, or
  plain `- ` bullet lines inside a section whose heading contains both
  "Acceptance" and "Criteria".
- **Events** — lines that start with `event:` (case-insensitive); the value
  after the colon is used verbatim.
- **AuthzModel** — the first line starting with `authz:` (case-insensitive).
